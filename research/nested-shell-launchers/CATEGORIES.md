# Nested GNOME Shell launchers: categories

84 launchers that start a nested GNOME Shell for extension development: 83 from 81 GitHub repos, with their URLs in `SOURCES.tsv`, their per-launcher details in `reviews/` and the per-question comparison in `COMPARISON.md`, and GNOME's `gnome-shell-test-tool`.

Categories:

1. Generic launchers: C1 in the review calls the launcher generic.
2. Project-bound previews: C1 binds the launcher to one project; it opens a window and is not mainly an automated test.
3. Project-bound test harnesses: C1 binds the launcher to one project; it runs headless or scripted, some also open a window.

Columns:

- Purpose (generic and test harness tables): what the launcher runs.
- Extension in: how the extension gets into the nested shell. "**real** data dir" means it lands in the real
  `~/.local/share/gnome-shell/extensions`, not in a sandbox.
- UUID: where the launcher takes the extension's UUID from.
- Enable: how the extension gets enabled in the nested shell.
- Settings: the GSettings backend: keyfile or memory backend, or dconf with the variable that moves its database and when
  the script sets it relative to the bus start. Checks the script makes follow after a semicolon.
- Bus: `dbus-run-session` alone means the script waits for it in the foreground, and the bus ends with the shell. The
  cell names any other form.
- Dirs: temp (new per run, removed afterwards), temp, kept (new per run, not removed), persistent (same path each run,
  kept between runs), none.
- Shell: devkit (GNOME 49+), nested (GNOME 48 and earlier), headless; the cell names how the launcher picks between them.
- Notes: other facts from the review.
